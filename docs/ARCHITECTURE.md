# Архитектура AgroConsult

## Состав системы

| Компонент | Технология | Назначение |
|---|---|---|
| Frontend | Next.js 14 + TypeScript + Tailwind | Веб-интерфейс пользователя и админ-панель |
| Backend API | FastAPI 0.115 + Python 3.11 | REST API, бизнес-логика, RAG-оркестрация |
| ORM | SQLAlchemy 2.0 async | Доступ к реляционной БД |
| Миграции | Alembic | Эволюция схемы |
| Реляционная БД | PostgreSQL 15 (Supabase) | Пользователи, сессии, документы, фидбек |
| Векторное хранилище | Qdrant Cloud | Эмбеддинги фрагментов НПА |
| Кэш | Upstash Redis (REST) | Кэширование ответов LLM |
| LLM + Embeddings | Sber GigaChat | Генерация и векторизация |
| Деплой бэкенда | Railway (nixpacks) | PaaS-хостинг |
| Деплой фронта | Vercel | CDN + serverless edge |

## Слои бэкенда

```
app/
├── core/        — конфиг, логирование, безопасность, bootstrap
├── db/          — async engine, базовый класс, миксины
├── models/      — SQLAlchemy ORM (User, Profile, Document, Chunk, Session, Message, Feedback)
├── schemas/     — Pydantic v2 (валидация запросов и сериализация ответов)
├── services/    — интеграции: GigaChat, Qdrant, Redis, ingestion, auth, chat
├── rag/         — RAG-пайплайн: parser → chunker → orchestrator + prompts
└── api/v1/      — HTTP-роуты (auth, profile, chat, documents, feedback)
```

## RAG-конвейер

1. **Препроцессинг** — нормализация вопроса, извлечение характеристик профиля.
2. **Embedding** — векторизация запроса через GigaChat Embeddings (1024 dim).
3. **Dense retrieval** — поиск top-15 фрагментов в Qdrant с фильтром по `is_active = true`.
4. **Сборка контекста** — top-6 фрагментов в пределах 4000 токенов; нумерация для цитат.
5. **Генерация** — chat completion в GigaChat-Pro со строгим системным промптом.
6. **Постобработка** — извлечение реально процитированных источников `[1]`, `[2]`.
7. **Кэширование** — ответ сохраняется в Redis на TTL = 1 час.
8. **Персистентность** — пользовательский вопрос и ответ ассистента записываются в `chat_messages`.

## Ключевые решения

### Почему dense retrieval без гибрида (BM25)
Размер корпуса ВКР (≈30 документов) делает гибридный поиск избыточным. Семантические эмбеддинги хорошо справляются с расхождением между разговорной формулировкой вопроса фермера и формальным языком НПА. Опционально добавляется в раздел «Перспективы развития».

### Почему BackgroundTasks вместо Celery
Индексация 30 документов занимает ≈2–3 минуты. Celery+Redis-as-broker — это +1 worker контейнер на Railway, +сложность деплоя. В MVP `FastAPI.BackgroundTasks` достаточно. При росте корпуса до 1000+ документов — миграция на Celery, инженерно тривиальная.

### Почему ленивая инициализация tiktoken
tiktoken скачивает BPE-файлы по сети при первом вызове. В офлайн-окружениях (например, CI без интернета) импорт модуля чанкера падал. Реализован fallback на char-based-оценку токенов, что не влияет на функциональность.

### Почему отдельная таблица `farmer_profiles`
Профиль фермера хранится в отдельной таблице 1:1 с `users`, чтобы:
- не загружать профиль при каждой аутентификации, если он не нужен;
- упростить аналитику без чтения чувствительной части пользователя;
- легко расширять профиль (новые поля) без миграций таблицы пользователей.

## Безопасность

- **JWT** с HS256, секрет в env, время жизни 7 дней
- **Bcrypt** для хранения паролей (cost = 12 по умолчанию)
- **OAuth2 Password Flow** для логина
- **Role-based access**: эндпоинты загрузки документов требуют `role = admin`
- **CORS** ограничен списком доменов из `CORS_ORIGINS`
- **TLS** end-to-end (Vercel, Railway, Supabase, Qdrant — всё HTTPS)
- **Параметризованные запросы** через SQLAlchemy — нет SQL-инъекций
- **Pydantic-валидация** на входе всех эндпоинтов

## Производительность

Целевые SLA для MVP:
- Latency p50 ответа /ask: < 3 сек (без кэша), < 200 мс (с кэшем)
- Latency p95 /ask: < 8 сек
- Throughput: 5 RPS на 2 gunicorn-воркерах Railway

Эмпирически основная задержка приходится на GigaChat (~1.5–2.5 сек на ответ ≈800 токенов).
